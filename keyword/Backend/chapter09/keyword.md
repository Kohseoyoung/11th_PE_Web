- Swagger / OpenAPI

  ### 1. 정의

  | 구분 | 정체 | 설명 |
      | --- | --- | --- |
  | OpenAPI | 규격 (약속된 문서 형식) | REST API를 설명하는 형식 |
  | Swagger | 도구 모음 | OpenAPI 규격을 바탕으로 REST API를 설계·개발·문서화·사용하도록 돕는 오픈소스 도구들 |

  | Swagger 주요 도구 | 역할 |
      | --- | --- |
  | Swagger Editor | 브라우저에서 OpenAPI 정의를 직접 작성하는 편집기 |
  | Swagger UI | OpenAPI 정의를 눌러 볼 수 있는 문서 화면으로 그려 줌 |
  | Swagger Codegen | OpenAPI 정의로 서버 뼈대 코드와 클라이언트 라이브러리를 생성 |

  ### 2. 동작 흐름

    ```
    ① 컨트롤러·DTO·어노테이션 작성
            ↓  서버 실행 시 라이브러리가 읽어 감
    ② OpenAPI JSON 생성  →  /v3/api-docs  (기계용 원본)
            ↓  Swagger UI가 이 JSON을 읽음
    ③ 문서 화면 표시    →  /swagger-ui.html  (사람용 화면)
    ```

    - springdoc-openapi는 실행 중에 애플리케이션을 살펴보고, Spring 설정, 클래스 구조, 어노테이션에서 API 정보를 추론한다.
    - 컨트롤러와 `@NotNull`, `@Size` 같은 검증 제약까지 읽어서 명세를 만든다.
    - 코드를 고치면 ②의 JSON이 바뀌고, ③의 화면도 같이 바뀐다.
    - 프론트엔드가 클라이언트 코드를 자동 생성할 때 쓰는 것은 ③의 화면이 아니라 ②의 JSON이다.

  ### 3. 주요 어노테이션

  | 어노테이션 | 역할 |
      | --- | --- |
  | `@Tag` | 컨트롤러 단위 묶음 이름 |
  | `@Operation` | API 하나의 요약과 설명 |
  | `@Schema` | DTO 필드 설명과 예시 값 |
  | `@ApiResponses` / `@ApiResponse` | 상태 코드별 응답 예시 |
  | `@SecurityRequirement` | 토큰이 필요한 API에 자물쇠 표시 |

  ### 4. 장단점

  | 장점 | 단점 |
      | --- | --- |
  | 코드에서 문서가 만들어져 코드와 문서가 어긋나지 않는다 | 설명과 실패 응답은 여전히 사람이 적어야 한다 |
  | Try it out으로 Postman 없이 바로 호출해 볼 수 있다 | 어노테이션이 많아지면 컨트롤러 코드가 길어진다 |
  | JSON 명세로 프론트엔드가 클라이언트 코드를 자동 생성할 수 있다 | 어노테이션에 적은 예시는 자동 검증이 안 되어 틀려도 모른다 |
- 단위 테스트

  ### 1. 정의

    - 단위 테스트는 시스템의 **작은 부분 하나**에 집중하는 낮은 수준의 테스트다.
        - "단위"의 기준은 느슨해서 클래스 하나, 함수 하나, 또는 밀접하게 연관된 클래스 몇 개가 될 수 있다.
    - 함께 동작하는 다른 객체는 가짜(Mock)로 바꿔서, 테스트하려는 클래스의 **판단(로직)만** 확인한다.

  ### 2. 두 가지 스타일

  | 구분 | Solitary (고립형) | Sociable (협력형) |
      | --- | --- | --- |
  | 협력 객체 | 가짜(테스트 더블)로 대체 | 진짜 객체를 그대로 사용 |
  | 특징 | 다른 클래스에 결함이 있어도 이 단위의 테스트는 실패하지 않는다 | 실제 협력까지 함께 검증한다  |
    - 이번 주 `FavoriteServiceTest`, `RatingServiceTest`는 Repository를 Mock으로 바꾼 **Solitary** 방식이다.

  ### 3. 주요 구성 요소 (JUnit 5 + Mockito)

  | 요소 | 역할 |
      | --- | --- |
  | `@ExtendWith(MockitoExtension.class)` | Mockito를 테스트에 연결한다 |
  | `@Mock` | 가짜 객체를 만든다 (예: 가짜 Repository) |
  | `@InjectMocks` | 가짜 객체를 주입받은 진짜 테스트 대상을 만든다 (예: Service) |
  | `given(...).willReturn(...)` | "이렇게 물어보면 이렇게 답해라"라고 상황을 설정한다 |
  | `assertThat`, `assertThatThrownBy` | 결과값이나 예외가 기대와 같은지 확인한다 |
  | `verify(..., never())` | 특정 메서드가 호출됐는지, 안 됐는지 확인한다 |

  ### 4. 장단점

  | 장점 | 단점 |
      | --- | --- |
  | 실행할 인프라가 없어서 진짜 단위 테스트는 보통 **매우 빠르게** 돈다 | URL 오타, 인증 설정 누락, DTO 검증 규칙 같은 연결 문제는 못 잡는다 |
  | DB가 꺼져 있어도 돈다 | Mock 설정이 실제 동작과 다르면 테스트는 통과해도 실제로는 틀릴 수 있다 |
  | "이미 즐겨찾기한 경우"처럼 만들기 어려운 상황을 쉽게 설정할 수 있다 | 내부 구현에 의존하면 코드 구조만 바꿔도 테스트가 깨질 수 있다 |
  | 실패하면 어느 로직이 틀렸는지 범위가 좁다  |  |
- 통합 테스트

  ### 1. 정의

    - 여러 구성 요소를 **진짜로 연결한 상태**에서, 요청부터 응답까지 전체 흐름이 맞게 동작하는지 확인하는 테스트다.
    - Spring은 통합 테스트를 애플리케이션 서버에 배포하거나 다른 외부 인프라에 연결하지 않고, Spring 컨테이너 위에서 돌리는 테스트로 정의한다.
    - 속도는 단위 테스트보다 느리지만, Selenium이나 원격 배포 테스트보다는 훨씬 빠르다.

  ### 2. 단위 테스트와 비교

  | 구분 | 단위 테스트 | 통합 테스트 |
      | --- | --- | --- |
  | 확인하는 것 | 클래스 하나의 판단(로직) | 요청부터 응답까지 전체 흐름 |
  | 함께 도는 것 | 없음 (Mock으로 대체) | 컨트롤러, 인터셉터, 검증, 서비스, DB까지 진짜 |
  | 속도 | 매우 빠름 | 느림 |
  | 알려주는 것 | 로직이 틀렸다 | 연결이 틀렸다 |

  ### 3. 통합 테스트만 잡을 수 있는 것

    - Bean 설정이 올바르게 연결되어 있는지
    - SQL, Hibernate 쿼리, JPA 엔티티 매핑이 맞는지
    - 트랜잭션 프록시가 설정한 대로 동작하는지
    - URL 오타, 인증 설정 누락, 요청 DTO 검증 규칙처럼 진짜 요청을 보내야 드러나는 문제

  ### 4. 주요 구성 요소

  | 요소 | 역할 |
      | --- | --- |
  | `@SpringBootTest` | Spring Boot의 `ApplicationContext` 전체를 올린다. 기본 모드는 실제 서버를 띄우지 않고 가짜 웹 환경으로 웹 컨텍스트를 올린다 |
  | `@AutoConfigureMockMvc` | 테스트에 주입할 수 있는 `MockMvc`를 자동으로 준비한다 |
  | `MockMvc` | 실제 서버를 띄우지 않고 웹 엔드포인트에 요청을 보내는 Spring MVC 테스트 도구 |
  | `@Transactional` | 테스트마다 트랜잭션을 만들고 끝나면 롤백해서, 테스트 중 바꾼 DB 데이터가 남지 않는다 |
  | H2 메모리 DB | 테스트할 때만 메모리에 만들어졌다 사라지는 DB라 개발 DB를 건드리지 않는다 |
  | `jsonPath("$.code")` | 응답 JSON에서 특정 필드를 꺼내 값을 확인한다  |
    - 롤백 덕분에 데이터를 지우거나 바꾼 테스트도 DB를 테스트 전 상태로 남겨서, 테스트끼리 서로 영향을 주지 않는다.

  ### 5. 장단점

  | 장점 | 단점 |
      | --- | --- |
  | 사용자 입장에서 실제로 무엇이 응답되는지 확인할 수 있다 | 컨텍스트를 올리고 DB를 쓰기 때문에 느리다 |
  | 인증, 검증, 매핑처럼 단위 테스트가 못 잡는 연결 문제를 잡는다 | 실패하면 어느 층에서 틀렸는지 범위가 넓어 원인 찾기가 어렵다 |
  | 엔티티 매핑과 DB 제약까지 함께 검증된다 | 테스트 DB 설정, 토큰 발급 같은 준비 작업이 필요하다 |
    - MockMvc 방식은 실제 서블릿 컨테이너보다 빠르지만, 컨테이너 자체에 의존하는 동작은 테스트할 수 없다.
    - 테스트가 서버끼리 주고받는 요청이라 브라우저 제약인 **CORS는 잡지 못한다**.
- Mock, Stub

  ### 1. 테스트 더블 (Test Double)

    - 테스트할 때 **진짜 객체 대신 끼워 넣는 대역**을 통틀어 테스트 더블이라고 한다. 영화의 스턴트 대역(stunt double)에서 따온 이름이다.
    - Mock과 Stub은 모두 테스트 더블의 한 종류다.

  | 종류 | 설명 |
      | --- | --- |
  | Dummy | 매개변수를 채우려고 넘기기만 하고 실제로는 쓰지 않는다 |
  | Fake | 실제로 동작하지만 지름길을 써서 운영에는 못 쓰는 구현이다. 메모리 테스트 DB가 그 예다 |
  | **Stub** | 테스트 중 호출되면 미리 준비한 답을 돌려준다. 그 테스트를 위해 설정하지 않은 호출은 대체로 무시한다 |
  | Spy | Stub이면서 자기가 어떻게 호출됐는지도 기록한다 |
  | **Mock** | 어떤 호출을 받아야 하는지에 대한 기대가 미리 들어 있다. 테스트가 끝난 뒤 기대한 호출을 모두 받았는지 검증한다  |

  ### 2. Mock과 Stub의 차이

  핵심 차이는 **무엇을 검증하느냐**다.

  | 구분 | Stub | Mock |
      | --- | --- | --- |
  | 역할 | 정해진 답을 돌려준다 | 호출이 기대대로 일어났는지 확인한다 |
  | 검증 방식 | **상태 검증**: 코드를 실행한 뒤 결과 상태를 확인한다 | **행위 검증**: 테스트 대상이 Mock에 기대한 호출을 했는지 확인한다 |
  | 질문 | "결과가 맞나?" | "그렇게 행동했나?" |

  ### 3. 이번 주 코드에서의 모습

  Mockito의 `@Mock`으로 만든 객체는 쓰는 방법에 따라 Stub도 되고 Mock도 된다.

  | 코드 | 역할 | 의미 |
      | --- | --- | --- |
  | `given(favoriteRepository.existsBy...(1L, 550L)).willReturn(true)` | Stub | "이미 즐겨찾기했다"고 정해진 답을 준다 |
  | `assertThat(response.movieId()).isEqualTo(550L)` | 상태 검증 | 결과값이 맞는지 확인한다 |
  | `verify(favoriteRepository, never()).save(any())` | Mock | `save`가 **호출되지 않았는지** 행위를 확인한다 |
    - 중복 테스트에서 예외 확인(상태)만 했다면, 예외를 던진 **뒤에** 저장하는 버그는 못 잡는다. `verify(never())`까지 써야 "저장하지 않았다"는 행위를 보장할 수 있다.
    - 통합 테스트에서 쓴 **H2 메모리 DB는 Fake**다. 실제로 SQL이 돌지만 운영용은 아니다.

  ### 4. 장단점

  | 장점 | 단점 |
      | --- | --- |
  | DB, 외부 API 없이 원하는 상황을 마음대로 만든다 | 가짜의 동작이 실제와 다르면 테스트는 통과해도 실제로는 틀릴 수 있다 |
  | Mock으로 "호출됐다/안 됐다"까지 검증할 수 있다 | Mock 검증이 많아지면 내부 구현에 묶여, 구조만 바꿔도 테스트가 깨진다 |
  | 테스트가 빠르고 결과가 매번 같다 | 설정 코드(`given`)가 길어질 수 있다 |
    - 실습 6의 `UnnecessaryStubbingException`이 Mockito의 엄격함을 보여 준다. 준비해 둔 Stub이 한 번도 쓰이지 않으면, 테스트와 코드가 어긋났다는 신호로 보고 실패시킨다.
- given-when-then

  ### 1. 정의

    - 테스트나 명세를 **세 덩어리로 나눠 쓰는 구조**다.
        - 예시를 통해 동작을 명세하는 방식이라고도 부른다.

  | 구분 | 의미 | 즐겨찾기 등록 예시 |
      | --- | --- | --- |
  | **given** | 테스트할 동작이 일어나기 **전의 상황** | 회원이 있고, 이 영화를 이미 즐겨찾기했다 |
  | **when** | 확인하고 싶은 **동작** | 즐겨찾기 등록을 호출한다 |
  | **then** | 그 동작으로 **기대하는 결과** | 409 예외가 나고, 저장은 호출되지 않는다 |
    - 한 덩어리에 조건이 여러 개면 보통 "And"로 잇는다.

  ### 2. 비슷한 패턴

  | 패턴 | 단계 |
      | --- | --- |
  | given-when-then | 상황 → 동작 → 결과 |
  | Arrange-Act-Assert (AAA) | 준비 → 실행 → 단언 |
  | Four-Phase Test | 준비 → 실행 → 검증 → 정리 |
    - 셋 다 사실상 같은 구조다. given-when-then은 명세를 전달하는 데 별 도움이 안 된다는 이유로 정리(Teardown) 단계를 뺐다.

  ### 3. 이번 주 코드에서의 모습

    ```java
    @Test
    @DisplayName("이미 즐겨찾기한 영화면 FAVORITE409_1 예외를 던지고 저장하지 않는다")
    void createFavoriteWhenDuplicated() {
        // given: 같은 회원이 같은 영화를 이미 즐겨찾기해 둔 상황
        given(memberRepository.findById(1L)).willReturn(Optional.of(member));
        given(favoriteRepository.existsByMember_MemberIdAndMovieId(1L, 550L)).willReturn(true);
    
        // when & then: 예외가 나고, 저장은 시도조차 하지 않는다
        assertThatThrownBy(() -> favoriteService.create(1L, new CreateFavoriteRequest(550L)))
                .isInstanceOf(ApiException.class);
        verify(favoriteRepository, never()).save(any(Favorite.class));
    }
    ```

    - Mockito의 `BDDMockito.given()`도 이 구조에서 이름을 따왔다. given 단계에서 Stub을 설정한다는 뜻이 코드에 그대로 드러난다.
    - 예외 테스트는 실행과 확인이 한 줄(`assertThatThrownBy`)에 묶여 `when & then`으로 합쳐 쓴다.

  ### 4. 장점

  | 장점 | 설명 |
      | --- | --- |
  | 읽기 쉽다 | 상황, 동작, 결과가 나뉘어 있어 처음 보는 사람도 흐름을 따라간다 |
  | 실패 원인이 바로 읽힌다 | `@DisplayName`을 이 문장 구조로 쓰면 실패했을 때 무엇이 깨졌는지 이름만 보고 안다 |
  | 테스트가 하나의 동작에 집중된다 | when이 하나라서 한 테스트에 여러 동작을 섞지 않게 된다 |
  | Postman 확인과 같은 생각 흐름이다 | "이 상태에서(given) 이걸 누르면(when) 이게 나와야 해(then)"를 그대로 옮긴 것이다 |
- 회귀 테스트

  ### 1. 정의

    - 코드를 고친 뒤에, **예전에 되던 기능이 지금도 되는지** 다시 확인하는 테스트다.
    - 회귀 테스트가 필요한 변경에는 버그 수정, 기능 개선, 설정 변경 등이 있다.

  ### 2. 확인 테스트와 비교

  ISTQB는 둘 다 구성 요소나 시스템이 수정되면서 시작되는 테스트인 변경 관련 테스트(change-related testing)로 묶는다.

  | 구분 | 확인 테스트 (Confirmation) | 회귀 테스트 (Regression) |
      | --- | --- | --- |
  | 질문 | "고친 버그가 정말 고쳐졌나?" | "고치다가 다른 데가 망가지지 않았나?" |
  | 대상 | 수정한 그 부분 | 수정하지 않은 기존 기능 전체 |

  ### 3. 왜 자동화하나

    - 기능이 늘수록 다시 확인할 것도 늘어난다. API 15개에 상황이 2~3개씩이면 확인할 조합이 금방 40개를 넘는다.
    - 회귀 테스트 묶음은 결함을 하나 찾을 때마다 커지는 경향이 있어서, 테스트 자동화를 함께 쓰는 경우가 많다.
    - Martin Fowler는 테스트 코드를 시스템 옆에 함께 만드는 "버그 탐지기"에 비유한다. 하루에 여러 번 돌리면 버그가 생긴 직후에 잡히고, 최근 변경만 보면 원인을 찾을 수 있다.

  ### 4. 장단점

  | 장점 | 단점 |
      | --- | --- |
  | 명령어 한 번으로 기존 기능 전체를 다시 확인한다 | 테스트를 작성하고 유지하는 비용이 든다 |
  | 버그가 생긴 직후에 잡혀 원인 범위가 좁다 | 테스트가 없는 부분은 망가져도 못 잡는다 |
  | 고쳐도 무엇이 깨지는지 바로 알 수 있어 리팩토링이 덜 무섭다 | 테스트가 많아지면 실행 시간이 길어진다 |
