- SOP와 CORS

  #### 1. SOP(Same-Origin Policy, 동일 출처 정책)

  #### 1-1. 정의

    - SOP는 브라우저가 기본으로 가지고 있는 보안 규칙이다. 한 출처에서 온 코드가 다른 출처의 데이터를 마음대로 가져가지 못하게 막는다.
    - 예를 들어 내가 메일 사이트에 로그인해 둔 상태에서 악성 사이트에 접속했다고 하자. 악성 사이트의 코드가 내 메일 내용을 읽어 가면 큰일이다. SOP는 이런 일을 막는다.
    - 브라우저는 여러 사이트를 동시에 열어 두기 때문에, 한 사이트가 위험해져도 다른 사이트의 데이터까지 새지 않도록 사이트마다 벽을 세워 두는 것이다.

  #### 1-2. 출처(Origin)란

  출처는 URL에서 프로토콜, 호스트, 포트 세 가지를 합친 것이다. 세 가지가 모두 같아야 같은 출처이고, 하나라도 다르면 다른 출처이다. 포트를 안 적으면 http는 80, https는 443이 자동으로 들어간다.

  기준 URL: `http://store.company.com/dir/page.html`

  | 비교 대상 | 결과 | 이유 |
      | --- | --- | --- |
  | `http://store.company.com/dir2/other.html` | 같은 출처 | 뒤의 경로만 다름 |
  | `https://store.company.com/page.html` | 다른 출처 | http와 https로 프로토콜이 다름 |
  | `http://store.company.com:81/dir/page.html` | 다른 출처 | 포트가 다름 |
  | `http://news.company.com/dir/page.html` | 다른 출처 | 호스트가 다름 |

  워크북의 `localhost:5173`(프론트)과 `localhost:8080`(백엔드)은 포트 번호가 달라서 다른 출처이다.

  #### 1-3. 다른 출처와는 어떤 행동이 되고 안 되나

  SOP는 모든 걸 막는 것이 아니라 행동의 종류에 따라 다르게 다룬다.

  | 행동 | 기본 동작 | 쉬운 설명 |
      | --- | --- | --- |
  | 쓰기 | 대체로 허용 | 다른 출처로 보내는 것. 링크 클릭, 폼 제출 |
  | 삽입 | 대체로 허용 | 다른 출처의 것을 내 화면에 끼워 넣는 것. 이미지, 스크립트, CSS, iframe |
  | 읽기 | 대체로 불허 | 다른 출처 서버의 응답 내용을 내 JS 코드로 꺼내 읽는 것 |
    - 보내거나 화면에 보여 주는 것은 되지만, 코드로 내용을 열어 보는 것만 막는 것이다.
    - 삽입은 내용을 못 읽어도 이미지 크기처럼 일부 정보가 드러날 수 있다.
    - localStorage, sessionStorage, IndexedDB는 출처마다 따로 분리되어 있어서 다른 출처의 것은 읽을 수 없다. 쿠키는 출처 대신 `Domain`, `Path` 같은 별도 규칙을 쓴다.
    - 출처가 다른 창끼리 안전하게 메시지를 주고받으려면 `window.postMessage`를 쓴다.

  #### 2. CORS(Cross-Origin Resource Sharing, 교차 출처 리소스 공유)

  #### 2-1. 정의

    - SOP는 기본적으로 다른 출처의 응답 읽기를 막는다. 그런데 프론트와 백엔드는 포트가 달라서 거의 항상 다른 출처이므로, 이걸 풀어 줄 방법이 필요하다. 그 방법이 CORS이다.
    - 서버가 응답에 "이 출처에서 온 요청은 괜찮다"는 내용을 헤더로 적어 보내면, 브라우저가 그걸 보고 응답을 JS에 넘겨 준다.
    - 막는 쪽은 서버가 아니라 브라우저이다. 요청은 서버에 정상적으로 도착하고 서버도 응답을 만든다. 하지만 브라우저가 응답을 JS에 전달하기 직전에 허락 표시가 없으면 가로막는다. 그래서 서버 로그에는 정상인데 화면에는 아무것도 안 뜨는 일이 생긴다.

  #### 2-2. 기본 동작 흐름

    1. 브라우저가 요청을 보낼 때 "나는 이 출처에서 왔다"는 뜻으로 `Origin` 헤더를 붙인다.
    2. 서버가 응답에 `Access-Control-Allow-Origin` 헤더로 "이 출처는 허용한다"를 적어 보낸다.
    3. 브라우저가 두 값을 비교해서 맞으면 응답을 JS에 넘기고, 맞지 않으면 막는다.

  #### 2-3. 요청의 세 가지 유형

  | 유형 | 쉬운 설명 | 조건 |
      | --- | --- | --- |
  | Simple Request | 확인 절차 없이 바로 보내는 요청 | GET, HEAD, POST 중 하나이고 기본 헤더만 사용. `Content-Type`은 `application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain` 중 하나 |
  | Preflight Request | 본 요청 전에 "이런 요청 보내도 되나요?" 하고 먼저 물어보는 요청 | simple 조건을 벗어나면 발생한다. 예: PUT, DELETE, `application/json`, 직접 만든 헤더. 질문은 `OPTIONS` 메서드로 보낸다 |
  | Credentialed Request | 쿠키나 로그인 정보를 함께 보내는 요청 | 요청에 `credentials: "include"`를 설정하고, 서버가 `Access-Control-Allow-Credentials: true`를 내려 주어야 한다 |
    - Preflight는 확인 질문 하나를 먼저 보내고, 서버가 허락하면 그다음에 진짜 요청을 보낸다. 허락하지 않으면 진짜 요청은 나가지 않는다.
    - Simple Request가 따로 정해진 이유는 HTML 폼이 예전부터 다른 출처로 이런 요청을 보낼 수 있었기 때문이다. 그래서 서버는 이미 이런 요청에 대한 위조(CSRF) 대비를 해야 했다.
    - 요즘 JSON을 주고받는 API는 `Content-Type`이 `application/json`이라서 대부분 Preflight가 먼저 발생한다고 보면 된다.
- Same-Origin과 Same-Site의 차이

  #### 1. Same-Origin(동일 출처)

  #### 1-1. 정의

    - 출처(origin)는 URL에서 프로토콜, 호스트(도메인), 포트를 합친 것이다.
    - 세 가지가 모두 똑같아야 같은 출처(same-origin)이고, 하나라도 다르면 다른 출처(cross-origin)이다.
    - 포트를 안 적으면 http는 80, https는 443이 자동으로 들어간 것으로 본다.
    - 같은 출처 여부는 아주 엄격하게 비교한다. 글자 하나, 번호 하나까지 맞아야 한다.

  #### 1-2. 판정 예시

  기준: `https://www.example.com:443`

  | 비교 대상 | 결과 | 이유 |
      | --- | --- | --- |
  | `https://www.evil.com:443` | 다른 출처 | 도메인 자체가 다름 |
  | `https://example.com:443` | 다른 출처 | `www`가 없어서 호스트가 다름 |
  | `https://login.example.com:443` | 다른 출처 | `login`이라는 서브도메인이 다름 |
  | `http://www.example.com:443` | 다른 출처 | https와 http로 프로토콜이 다름 |
  | `https://www.example.com:80` | 다른 출처 | 포트가 다름 |
  | `https://www.example.com` | 같은 출처 | 포트를 안 적어도 443이 자동으로 들어가서 같음 |

  #### 2. Same-Site(동일 사이트)

  #### 2-1. 용어 정리

  사이트는 도메인의 "가장 중요한 이름 부분"만 보는 개념이다. 이 부분을 알아내려면 먼저 아래 용어를 알아야 한다.

  | 용어 | 쉬운 설명 | 예시 |
      | --- | --- | --- |
  | TLD | 도메인 맨 끝의 최상위 도메인 | `.com`, `.kr` |
  | eTLD | 이름 하나가 아니라 여러 칸으로 이루어진 도메인 끝부분. 어디까지가 끝부분인지는 Public Suffix List라는 목록에 정해져 있다 | `.co.jp`, `.github.io` |
  | eTLD+1 | eTLD와 그 바로 앞 한 칸을 합친 것. MDN은 "등록 가능 도메인(registrable domain)"이라고도 부른다 | `example.com` |
  | 사이트(site) | 프로토콜 + eTLD+1 | `https://example.com` |

  예시로 보면 이렇다.

    - `https://www.example.com:443/foo`는 `.com`이 끝부분이고 그 앞 한 칸이 `example`이므로, 사이트는 `https://example.com`이다. `www`와 포트는 사이트에 포함되지 않는다.
    - `https://www.project.github.io:443/foo`는 `.github.io`가 끝부분이므로, 그 앞 한 칸인 `project`까지 합쳐 사이트가 `https://project.github.io`이다.
    - 그래서 `your-project.github.io`와 `my-project.github.io`는 서로 다른 사이트다. 한 사람이 쓰는 도메인이 아니라 여러 사람이 나눠 쓰는 서비스이기 때문이다.

  #### 2-2. 판정 예시

  기준: `https://www.example.com:443`

  | 비교 대상 | 결과 | 이유 |
      | --- | --- | --- |
  | `https://www.evil.com:443` | 다른 사이트 | 도메인이 다름 |
  | `https://login.example.com:443` | 같은 사이트 | 서브도메인(`login`)은 무시하고 `example.com`만 비교 |
  | `http://www.example.com:443` | 다른 사이트 | 프로토콜이 다름 |
  | `https://www.example.com:80` | 같은 사이트 | 포트는 무시 |
  | `https://www.example.com` | 같은 사이트 | 포트는 무시 |

  #### 3. 두 개념의 차이

  쉽게 말해 출처는 "정확히 같은 곳인가"를 보고, 사이트는 "같은 서비스(회사)인가"를 본다. 회사에 비유하면 `example.com`이 회사이고 `login`, `www` 같은 서브도메인은 그 회사의 부서와 비슷하다. 출처는 부서까지 똑같아야 같다고 보고, 사이트는 같은 회사이기만 하면 같다고 본다.

  | 구분 | Same-Origin | Same-Site |
      | --- | --- | --- |
  | 무엇을 비교하나 | 프로토콜 + 호스트 전체 + 포트 | 프로토콜 + 등록 가능 도메인(eTLD+1) |
  | 서브도메인이 다르면 | 다른 출처 | 같은 사이트 |
  | 포트가 다르면 | 다른 출처 | 같은 사이트 |
  | 얼마나 엄격한가 | 더 엄격함 | 더 느슨함 |
  | 둘의 관계 | 같은 출처이면 항상 같은 사이트이다 | 같은 사이트라도 다른 출처일 수 있다 |
  | 주로 쓰이는 곳 | 스크립트가 다른 곳의 데이터를 읽어도 되는지 판단 (SOP, CORS) | 쿠키를 요청에 실어 보낼지 판단 (SameSite 쿠키) |

  MDN은 두 개념을 이렇게 구분한다.

    - 출처는 "스크립트가 어떤 리소스에 접근할 수 있는지" 같은 보안 판단에 쓰이는 더 좁고 엄격한 개념이다.
    - 사이트는 등록 가능 도메인(경우에 따라 프로토콜 포함)만 보고, 서브도메인과 포트는 무시하는 더 넓은 개념이다.
- 쿠키의 SameSite 속성

  #### 1. SameSite란

    - `SameSite`는 쿠키에 붙이는 속성으로, 다른 사이트에서 시작된 요청(cross-site 요청)에 그 쿠키를 실어 보낼지 정한다.
    - 쿠키는 원래 요청마다 자동으로 붙기 때문에, 악성 사이트가 로그인된 사용자의 쿠키를 이용해 요청을 보내는 CSRF 공격이 가능하다. SameSite는 이를 막는 데 도움이 된다.
    - 같은 사이트인지는 등록 가능 도메인(eTLD+1)과 프로토콜로 판단한다. 서브도메인과 포트는 무시한다.

  #### 2. 설정 방법

    ```
    Set-Cookie: 이름=값; SameSite=Strict
    Set-Cookie: 이름=값; SameSite=Lax
    Set-Cookie: 이름=값; SameSite=None; Secure
    ```

  #### 3. 세 가지 값

  | 값 | 쿠키를 보내는 경우 | 용도 |
      | --- | --- | --- |
  | Strict | 같은 사이트에서 시작된 요청만. 다른 사이트의 링크로 들어와도 안 보냄 | 비밀번호 변경, 결제 같은 민감한 동작 |
  | Lax | 같은 사이트 요청 + 링크 클릭 같은 최상위 이동(GET) | 화면 표시에 영향을 주는 쿠키 |
  | None | 모든 요청. 반드시 `Secure`와 함께 사용 | 위젯, 임베드, 광고, 다른 사이트 로그인 |

  #### 4. Lax의 전송 조건

  다른 사이트에서 온 요청에 쿠키를 보내려면 **최상위 이동**(주소창 URL이 바뀌는 이동: 링크 클릭, 폼 제출)이고 **안전한 메서드**(POST, PUT, DELETE 제외)여야 한다. `fetch`, `<img>`, `<script>`, `<iframe>` 요청에는 보내지 않는다.

  #### 5. 알아둘 점

    - `None`은 `Secure`(HTTPS 전용)가 필수이다. 없으면 브라우저가 쿠키를 거부한다.
    - 속성을 안 적으면 브라우저가 Lax로 취급하는 곳이 많다. 다만 브라우저마다 다를 수 있으므로 직접 적기를 권장한다.
    - SameSite만으로 완전히 안전해지지 않으므로 쿠키 내용은 서버에서 검증해야 하고, 비밀 값은 쿠키에 저장하면 안 된다.

  #### 6. CORS와의 차이

  | 구분 | CORS | SameSite 쿠키 |
      | --- | --- | --- |
  | 기준 | 같은 출처인가 (포트까지 비교) | 같은 사이트인가 (포트, 서브도메인 무시) |
  | 막는 대상 | 응답을 JS가 읽는 것 | 요청에 쿠키가 실리는 것 |
- 복합 UNIQUE 제약을 사용하는 이유는?

  #### 1. 복합 UNIQUE 제약이란

    - UNIQUE 제약은 인덱스에 들어가는 값이 모두 서로 달라야 한다는 규칙이다. 같은 값을 넣으면 MySQL이 에러를 낸다.
    - 복합 UNIQUE는 컬럼을 두 개 이상 묶어서, 그 **조합**이 유일해야 한다는 뜻이다. 컬럼 값 하나하나는 겹쳐도 되고, 조합이 같을 때만 막는다.

  #### 2. 사용하는 이유

  워크북에서는 한 회원이 같은 영화에 평점을 한 번만 남길 수 있고, 같은 영화를 중복으로 즐겨찾기할 수 없다. 다만 여러 회원이 같은 영화에 남기는 것과, 한 회원이 여러 영화에 남기는 것은 가능해야 한다.

  | 걸어 둔 제약 | 결과 |
      | --- | --- |
  | `movie_id`만 UNIQUE | 영화당 평점이 전체 회원을 통틀어 하나뿐이다 |
  | `member_id`만 UNIQUE | 회원당 평점이 하나뿐이다 |
  | `(member_id, movie_id)` 복합 UNIQUE | 회원마다 영화당 하나씩만 가능하다 |

  #### 3. 코드

    ```sql
    UNIQUE KEY uk_rating_member_movie (member_id, movie_id)
    ```

    ```java
    @Table(name = "rating",
           uniqueConstraints = @UniqueConstraint(columnNames = {"member_id", "movie_id"}))
    ```

  #### 4. 알아둘 점

    - UNIQUE는 NULL이 가능한 컬럼에 NULL을 여러 개 허용한다. 중복을 막으려는 컬럼은 `NOT NULL`로 두는 것이 안전하다.
    - 앱에서 먼저 조회해서 확인하는 것만으로는 동시 요청 시 중복이 생길 수 있다. DB 제약이 마지막 방어선이다.
- 외부 Open API 연동 시 API Key를 프론트/백엔드 중 어디에 두어야 안전한가?

  #### 1. 결론

    - API Key는 **백엔드(서버)에 두는 것이 안전하다.**
    - 프론트(브라우저) 코드에 넣으면 사용자가 누구든 볼 수 있다.
        - 브라우저로 내려온 JS 코드와 네트워크 요청은 개발자 도구에서 그대로 확인할 수 있기 때문이다.
    - Google Cloud 공식 문서도 키를 클라이언트 코드에 넣거나 저장소에 커밋하지 말라고 한다. 대신 서버가 키를 보관하고 외부 API를 호출하며, 클라이언트는 그 서버를 호출하는 구조를 권장한다.

  #### 2. 비교

  | 구분 | 프론트에 둠 | 백엔드에 둠 |
      | --- | --- | --- |
  | 키 노출 | 코드와 요청에서 누구나 볼 수 있다 | 브라우저로 내려가지 않는다 |
  | 키 유출 시 | 다른 사람이 내 키로 외부 API를 마음대로 호출할 수 있다 | 서버 접근이 뚫리지 않는 한 안전하다 |
  | 구조 | 프론트 → 외부 API | 프론트 → 우리 서버 → 외부 API |

  #### 3. 서버에서 키를 다룰 때

  | 원칙 | 설명 | 출처 |
      | --- | --- | --- |
  | 코드에 직접 쓰지 않기 | 소스 코드나 설정 파일에 평문으로 넣거나 커밋하면 안 된다. 커밋 이력에 남아 지우기도 어렵다 | OWASP |
  | 별도 보관소 사용 | 비밀 관리 서비스(secrets manager)에 모아 두는 것을 권장한다. 환경변수는 최후의 수단이라고 한다 | OWASP |
  | URL에 넣지 않기 | 쿼리 파라미터 대신 HTTP 헤더로 보낸다. URL은 로그에 남기 쉽다 | Google Cloud |
  | 사용 범위 제한 | 키를 쓸 수 있는 곳과 API를 제한해 유출돼도 피해를 줄인다 | Google Cloud |
  | 정기적으로 교체 | 주기적으로 새 키로 바꾸고, 노출되면 즉시 폐기한다 | OWASP, Google Cloud |
  | 로그에 남기지 않기 | 키를 로그에 찍지 않는다 | OWASP |

  워크북에서 DB 비밀번호를 `${DB_PASSWORD}` 환경변수로 처리한 것도 같은 원칙이다. 학습용 프로젝트에서는 환경변수와 `.gitignore`로 충분하지만, 실서비스에서는 OWASP의 권장대로 비밀 관리 서비스를 쓰는 것이 낫다.
