- Web Storage
    - localStorage와 sessionStorage는 저장값의 수명과 공유 범위가 어떻게 다른가요?

      #### 1. Web Storage란?

      Web Storage API는 브라우저 안에 **문자열 key와 value를 저장하는 기능**이다. 서버에 보내지 않고 사용자의 브라우저에만 저장된다. 종류는 localStorage와 sessionStorage 두 가지이며, 사용법은 같고 **저장값이 얼마나 오래 남는지**와 **어디까지 공유되는지**가 다르다.

      두 저장소 모두 **origin 단위**로 나뉜다. origin은 protocol, host, port가 모두 같은 주소 범위를 뜻한다.

      | 주소 | 같은 origin인가? |
              | --- | --- |
      | `http://localhost:5173/movies` 와 `http://localhost:5173/search` | 같다. 경로는 달라도 된다. |
      | `http://localhost:5173` 와 `http://localhost:3000` | 다르다. port가 다르다. |
      | `http://example.com` 와 `https://example.com` | 다르다. protocol이 다르다. |

      #### 2. 저장값의 수명

      **1) localStorage**

        - 직접 지우기 전까지 계속 남는다.
        - 새로고침해도, 탭을 닫아도, 브라우저를 껐다 켜도 유지된다.
        - 지워지는 경우는 코드로 `removeItem`을 호출하거나, 사용자가 개발자 도구나 브라우저 설정에서 삭제할 때다.

      **2) sessionStorage**

        - 현재 탭이 열려 있는 동안만 남는다.
        - 새로고침해도 유지되지만, 탭이나 창을 닫으면 사라진다.
        - 다시 열면 비어 있는 상태로 시작한다.

      #### 3. 공유 범위

      **1) localStorage**

        - 같은 origin이면 **모든 탭과 창이 같은 값을 공유**한다.
        - 한 탭에서 저장하면 다른 탭에서도 바로 읽을 수 있다.

      **2) sessionStorage**

        - 같은 origin이어도 **탭마다 따로** 가진다.
        - 같은 사이트를 탭 두 개로 열면 각 탭이 자기만의 저장소를 쓴다. 한 탭에서 저장한 값은 다른 탭에서 볼 수 없다.

      #### 4. 한눈에 비교

      | 구분 | localStorage | sessionStorage |
              | --- | --- | --- |
      | 수명 | 직접 지우기 전까지 유지 | 탭이 열려 있는 동안만 유지 |
      | 새로고침 | 유지된다. | 유지된다. |
      | 탭을 닫은 뒤 | 유지된다. | 사라진다. |
      | 브라우저를 껐다 켠 뒤 | 유지된다. | 사라진다. |
      | 공유 범위 | 같은 origin의 모든 탭과 창 | 해당 탭 안에서만 |
      | 적합한 값 | 다음 방문에도 필요한 값 | 현재 작업 중에만 필요한 임시 값 |
    - 객체나 배열을 저장할 때 JSON 문자열로 바꿔야 하는 이유는 무엇일까요?

      #### 객체나 배열을 저장할 때 JSON 문자열로 바꿔야 하는 이유

      **1. Web Storage는 문자열만 저장한다**

      localStorage와 sessionStorage는 key와 value를 모두 **문자열**로 저장하도록 만들어진 저장소다. `setItem(key, value)`의 value 자리에는 문자열이 들어와야 한다.

      배열과 객체는 문자열이 아니라 JavaScript가 메모리에서 다루는 값이다. 이 값을 저장소에 넣으려면 먼저 문자열로 바꿔야 한다.

        - **직렬화(serialization)**: 값을 저장하거나 전송할 수 있는 형태로 바꾸는 것이다. `JSON.stringify`가 맡는다.
        - **역직렬화(deserialization)**: 저장된 값을 원래 값으로 되돌리는 것이다. `JSON.parse`가 맡는다.

      **2. 그대로 넣으면 어떻게 될까?**

      문자열이 아닌 값을 `setItem`에 넣으면 브라우저는 오류를 내지 않고 **자동으로 문자열로 바꿔서 저장**한다. 문제는 이때 값이 의도와 다르게 변한다는 점이다.

        ```jsx
        localStorage.setItem("umcine-bookmarks", [2, 7]);
        localStorage.getItem("umcine-bookmarks");   // "2,7"
        
        localStorage.setItem("movie", { id: 2, title: "오디세이" });
        localStorage.getItem("movie");              // "[object Object]"
        ```

        - 배열은 요소를 쉼표로 이은 `"2,7"`이 된다. 배열이었다는 정보가 사라진다.
        - 객체는 `"[object Object]"`라는 고정된 문자열이 된다. 안에 있던 `id`와 `title`이 모두 사라져서 복구할 수 없다.

      #### 3. 쉼표 문자열로는 배열을 제대로 복원할 수 없다

      `"2,7"`을 `split(",")`으로 쪼개면 되지 않을까 싶지만 여러 문제가 생긴다.

      | 문제 | 예시 | 결과 |
              | --- | --- | --- |
      | 숫자가 문자열이 된다. | `"2,7".split(",")` | `["2", "7"]` (숫자가 아니라 문자열) |
      | 빈 배열을 복원할 수 없다. | `[].toString()`은 `""`이고, `"".split(",")` | `[""]` (빈 배열이 아니라 빈 문자열 하나가 든 배열) |
      | 중첩 구조가 사라진다. | `[[1, 2], [3]].toString()` | `"1,2,3"` (안쪽 배열 구분이 없어진다) |
      | 값에 쉼표가 있으면 쪼개진다. | `["a,b", "c"].toString()` | `"a,b,c"` (원래 요소가 2개였는지 알 수 없다) |

      첫 번째 문제는 북마크에서 바로 버그가 된다. 저장된 ID가 문자열 `"2"`로 복원되면 `bookmarkedMovieIds.includes(2)`가 `false`가 된다. 분명 북마크했는데 화면에서는 해제된 상태로 보이는 것이다. JavaScript에서 숫자 `2`와 문자열 `"2"`는 서로 다른 값이기 때문이다.

      #### 4. JSON은 구조와 타입을 함께 저장한다

      JSON(JavaScript Object Notation)은 값의 **구조와 타입을 문자열 안에 그대로 표현하는 약속된 형식**이다. 문자열로 바뀌어도 나중에 원래 모양으로 정확히 되돌릴 수 있다.

      | 원래 값 | JSON 문자열 | 복원 결과 |
              | --- | --- | --- |
      | `[2, 7]` | `"[2,7]"` | `[2, 7]` (숫자 유지) |
      | `["2", "7"]` | `"[\"2\",\"7\"]"` | `["2", "7"]` (문자열 유지) |
      | `[]` | `"[]"` | `[]` (빈 배열 유지) |
      | `[[1, 2], [3]]` | `"[[1,2],[3]]"` | `[[1, 2], [3]]` (중첩 유지) |
      | `{ id: 2, title: "오디세이" }` | `"{\"id\":2,\"title\":\"오디세이\"}"` | 같은 객체 |

      숫자, 문자열, 불린, `null`, 배열, 객체를 구분해서 적기 때문에 복원했을 때 타입이 바뀌지 않는다.

      #### 5. JSON을 쓰는 이유

        1. **Web Storage의 제한을 지킨다.** 결과가 문자열이라 저장소에 그대로 넣을 수 있다.
        2. **복원이 정확하다.** 타입, 빈 배열, 중첩 구조가 유지된다. 직접 만든 쉼표 규칙처럼 값에 따라 깨지지 않는다.
        3. **내장 기능으로 간단히 처리된다.** 별도 라이브러리나 변환 규칙 없이 `JSON.stringify`와 `JSON.parse`만 쓰면 된다.
        4. **표준 형식이다.** 프로그래밍 언어와 상관없이 널리 쓰이고, 5주차부터 서버와 주고받는 API 데이터도 JSON이다.
        5. **사람이 읽을 수 있다.** Application 패널에서 저장값이 그대로 보여서 디버깅하기 쉽다.
    - Web Storage에는 어떤 데이터를 저장하는 것이 적절할까요?

      #### 1. 저장하기 적절한 데이터

      Web Storage는 **브라우저에서만 필요한 작은 값**을 저장하기에 적절하다. 서버가 기준이 되는 데이터가 아니라 브라우저가 기준이 되는 **클라이언트 상태**가 대상이다.

      | 데이터 | 저장소 | 이유 |
              | --- | --- | --- |
      | 북마크한 영화 ID 목록 | localStorage | 다음 방문에도 유지되어야 한다. |
      | 영화 카드 크기, 정렬 방식 같은 화면 설정 | localStorage | 사용자가 정한 설정을 계속 기억해야 한다. |
      | 다크 모드 같은 테마 설정 | localStorage | 방문할 때마다 다시 고르지 않게 한다. |
      | 입력 중인 폼 임시 저장 | sessionStorage | 현재 탭에서 작업하는 동안만 필요하다. |
      | 탭 안에서만 쓰는 필터나 단계 값 | sessionStorage | 탭을 닫으면 초기화되어도 괜찮다. |

      #### 2. 저장하기 적절하지 않은 데이터

      | 데이터 | 이유 |
              | --- | --- |
      | 인증 토큰, 비밀번호 | 사용자가 개발자 도구에서 볼 수 있고, 악성 스크립트가 같은 origin에서 읽어 갈 위험이 있다. |
      | 개인정보 | 브라우저에 평문으로 남아 있어 보호되지 않는다. |
      | 서버가 기준인 데이터 (API로 받는 영화 목록, 사용자 정보) | 복사해 두면 서버의 최신 값과 어긋나서 어느 쪽이 맞는지 판단하기 어려워진다. 서버 상태는 6주차부터 TanStack Query로 관리한다. |
      | 크기가 큰 데이터 | 값을 읽고 쓰는 동안 JavaScript 코드가 기다리므로, 큰 데이터를 자주 저장하면 화면이 느려질 수 있다. 용량도 제한적이다. |
      | 여러 기기나 사용자와 공유해야 하는 데이터 | Web Storage는 해당 브라우저에만 저장된다. 다른 기기에서는 볼 수 없다. |

      #### 3. 저장 여부를 정하는 기준

        1. **브라우저에서만 필요한 값인가?** 서버가 기준이면 저장하지 않는다.
        2. **작은 값인가?** 영화 ID 몇 개처럼 작은 값만 저장한다.
        3. **민감한 정보가 아닌가?** 토큰, 비밀번호, 개인정보는 저장하지 않는다.
        4. **얼마나 오래 필요한가?** 다음 방문에도 필요하면 localStorage, 현재 탭에서만 필요하면 sessionStorage를 쓴다.
- 클라이언트 상태와 전역 상태 관리
    - 컴포넌트 상태와 전역 상태는 사용하는 범위가 어떻게 다른가요?

      #### 1. 컴포넌트 상태 (로컬 상태)

      한 컴포넌트 안에서 만들고, 그 컴포넌트가 직접 읽고 바꾸는 상태다. React에서는 `useState`로 관리한다.

        - 상태를 만든 컴포넌트와 props로 전달받은 자식 컴포넌트만 값을 알 수 있다.
        - 다른 화면이나 상관없는 컴포넌트는 이 값을 모른다.
        - 컴포넌트가 화면에서 사라지면 상태도 함께 사라진다.
        - 입력값, 모달 열림 여부, 토글 상태처럼 **한 컴포넌트 안에서만 필요한 값**에 적합하다.

        ```tsx
        function MovieCard() {
          const [isOpen, setIsOpen] = useState(false);   // 이 컴포넌트만 아는 값
          // ...
        }
        ```

      #### 2. 전역 상태

      앱의 **여러 위치에서 읽고 바꿔야 하는 상태**다. 컴포넌트 바깥에 있는 store에 보관하고, 필요한 컴포넌트가 직접 꺼내 쓴다. 이번 주차에서는 Zustand store가 전역 상태를 담당한다.

        - 목록, 검색, 상세처럼 서로 다른 라우트의 컴포넌트가 **같은 값**을 공유한다.
        - 한 곳에서 값을 바꾸면 그 값을 쓰는 모든 컴포넌트에 반영된다.
        - 특정 컴포넌트가 사라져도 store의 값은 남아 있다.
        - 북마크 ID 목록처럼 **여러 화면이 함께 쓰는 값**에 적합하다.

        ```tsx
        const isBookmarked = useBookmarkStore((state) =>
          state.bookmarkedMovieIds.includes(movieId),
        );
        ```

      #### 3. 한눈에 비교

      | 구분 | 컴포넌트 상태 | 전역 상태 |
              | --- | --- | --- |
      | 사용하는 범위 | 상태를 만든 컴포넌트와 그 자식 | 앱의 여러 컴포넌트와 라우트 |
      | 보관하는 위치 | 컴포넌트 안 | 컴포넌트 바깥의 store |
      | 도구 | `useState` | Zustand |
      | 값이 사라지는 때 | 컴포넌트가 사라질 때 | 앱이 종료되거나 새로고침될 때 |
      | 적합한 값 | 입력값, 모달 열림 여부 | 북마크 목록 |
    - 여러 화면에서 사용하는 북마크 상태를 전역으로 관리하면 어떤 장점과 비용이 생길까요?

      #### 1. 전역으로 관리한다는 것

      북마크 ID 목록(`bookmarkedMovieIds`)과 이를 바꾸는 함수(`toggleBookmark`)를 컴포넌트 안이 아니라 **컴포넌트 바깥의 Zustand store**에 두고, 목록·검색·상세 화면이 모두 같은 store를 꺼내 쓰는 방식이다.

        ```
        목록 화면 ─┐
        검색 화면 ─┼─ Zustand store (bookmarkedMovieIds, toggleBookmark)
        상세 화면 ─┘
        ```

      #### 2. 장점

      **1) 모든 화면이 같은 값을 본다**

      상태가 store에 하나만 있으므로 어느 화면에서 북마크하거나 해제해도 다른 화면에 같은 결과가 보인다. 컴포넌트마다 `useState`를 따로 두면 각자 값을 가져 서로 어긋날 수 있지만, 전역 상태는 이 문제가 구조적으로 생기지 않는다.

      **2) props를 여러 단계로 내려주지 않아도 된다**

      상태를 공통 부모에 두는 방식은 값과 함수를 필요한 컴포넌트까지 props로 계속 전달해야 한다. 라우트가 다른 화면은 공통 부모가 앱 전체가 되어 구조가 복잡해진다. 전역 store를 쓰면 필요한 컴포넌트가 직접 꺼내 쓴다.

      **3) 상태와 변경 로직이 한 곳에 모인다**

      북마크를 추가하고 제거하는 규칙이 `bookmark-store.ts`의 `toggleBookmark` 하나에만 있다. 화면마다 같은 로직을 복사해서 만들 필요가 없고, 규칙을 바꿀 때도 한 곳만 고치면 된다.

      **4) 필요한 값만 골라 써서 불필요한 렌더링을 줄일 수 있다**

      selector로 필요한 값만 고르면, 그 값이 바뀔 때만 해당 컴포넌트가 다시 그려진다. 예를 들어 `BookmarkButton`은 현재 영화가 북마크되었는지만 구독한다.

        ```tsx
        const isBookmarked = useBookmarkStore((state) =>
          state.bookmarkedMovieIds.includes(movieId),
        );
        ```

      **5) 저장 기능을 한 번에 붙일 수 있다**

      store에 `persist`를 적용하면 상태가 바뀔 때마다 localStorage에 저장되고, 앱을 다시 열면 복원된다. 화면마다 저장 코드를 따로 작성하지 않아도 된다.

      #### 3. 비용

      **1) 라이브러리와 구조가 추가된다**

      Zustand를 설치하고 store 파일을 만들어야 한다. `useState`만 쓸 때보다 파일과 개념(store, action, selector)이 늘어난다.

      **2) 상태가 어디서 바뀌는지 추적하기 어려워질 수 있다**

      어느 컴포넌트에서든 `toggleBookmark`를 호출할 수 있으므로, 값이 바뀐 원인을 찾으려면 호출하는 곳을 모두 확인해야 한다. 컴포넌트 안에 상태가 있으면 그 컴포넌트만 보면 된다.

      **3) 컴포넌트가 store에 의존한다**

      `BookmarkButton`이 store를 직접 읽으면 `movieId`만 넘겨서 쓸 수 있어 편하지만, store 없이는 단독으로 동작하지 않는다. 다른 프로젝트로 옮기거나 테스트할 때 store를 함께 준비해야 한다.

      **4) 저장 데이터를 관리해야 한다**

      `persist`를 쓰면 상태가 localStorage에 남는다. 그래서 다음을 신경 써야 한다.

        - 저장값은 사용자가 개발자 도구에서 바꾸거나 지울 수 있다.
        - 상태 구조를 바꾸면 이전에 저장된 값과 맞지 않을 수 있다. 이때는 `name`을 바꾸거나 `version`을 관리한다.
        - 저장할 값만 `partialize`로 골라야 한다. 함수까지 저장하려 하면 안 된다.

      **5) 모든 값을 전역에 넣으면 오히려 복잡해진다**

      모달 열림 여부처럼 한 컴포넌트에서만 쓰는 값까지 전역에 두면 store만 커지고 이득이 없다. 서버가 기준인 데이터를 store에 복사하면 어느 값이 최신인지 판단하기 어려워진다.

    - Zustand와 Web Storage는 북마크 상태를 관리할 때 각각 어떤 역할을 할까요?

      #### 1. Zustand의 역할: 화면 사이에서 상태를 공유한다

      Zustand는 컴포넌트 바깥에 **store**를 만들어 상태를 보관한다. 목록, 검색, 상세 화면이 모두 같은 store를 꺼내 쓰므로 어느 화면에서 북마크해도 다른 화면에 같은 결과가 보인다.

        - `bookmarkedMovieIds`: 북마크한 영화 ID 배열을 보관한다.
        - `toggleBookmark`: 북마크를 추가하거나 제거하는 action이다.
        - selector: 컴포넌트가 필요한 값만 골라 쓰게 한다.

        ```tsx
        const isBookmarked = useBookmarkStore((state) =>
          state.bookmarkedMovieIds.includes(movieId),
        );
        const toggleBookmark = useBookmarkStore((state) => state.toggleBookmark);
        ```

      Zustand의 상태는 **메모리**에 있다. 새로고침하거나 브라우저를 닫으면 사라지므로 Zustand만으로는 북마크가 유지되지 않는다.

      #### 2. Web Storage의 역할: 새로고침 뒤에도 값을 유지한다

      localStorage는 북마크 ID를 **브라우저에 저장**해서 새로고침이나 브라우저 재실행 뒤에도 값이 남게 한다.

        - 배열은 `JSON.stringify`로 문자열로 바꿔 저장한다.
        - 읽을 때는 `JSON.parse`로 배열로 되돌린다.
        - 값은 사용자가 개발자 도구에서 바꿀 수 있으므로 읽을 때 기본값과 오류 처리를 준비한다.

      Web Storage는 값을 보관만 할 뿐, 컴포넌트에 변경을 알리거나 여러 화면이 같은 값을 쓰게 해 주지는 않는다.

      #### 3. 정리

      | 구분 | Zustand | Web Storage (localStorage) |
              | --- | --- | --- |
      | 하는 일 | 여러 컴포넌트가 같은 상태를 공유한다. | 값을 브라우저에 저장한다. |
      | 값이 있는 곳 | 메모리 (store) | 브라우저 저장소 |
      | 화면 간 공유 | 가능하다. | 직접 읽어야 하며 변경이 자동으로 반영되지 않는다. |
      | 새로고침 후 | 사라진다. | 유지된다. |
      | 상태가 바뀌면 화면 갱신 | 구독한 컴포넌트가 다시 그려진다. | 화면이 갱신되지 않는다. |
      | 북마크에서의 역할 | 목록, 검색, 상세가 같은 북마크 상태를 본다. | 새로고침 뒤에도 북마크가 남는다. |
