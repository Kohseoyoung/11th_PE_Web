- PK, FK란?

  ### 1. PK (Primary Key, 기본키)

    - 테이블에서 각 행을 고유하게 식별하는 값.
    - **조건**
        - 중복 불가
        - NULL 불가
        - 테이블당 1개
    - **예시**


        | id (PK) | 이름 | 이메일 |
        | --- | --- | --- |
        | 1 | 김철수 | kim@a.com |
        | 2 | 이영희 | lee@a.com |
    
    ### 2. FK (Foreign Key, 외래키)
    
    - 다른 테이블의 PK를 참조하는 컬럼. 테이블 간 관계를 만든다.
    - **특징**
        - 중복 가능
        - NULL 가능
        - 테이블당 여러 개 가능
    - **예시**
        
        
        | id (PK) | 제목 | writer_id (FK) |
        | --- | --- | --- |
        | 1 | 안녕하세요 | 1 |
        | 2 | 질문있어요 | 1 |
        | 3 | 반갑습니다 | 2 |
    - **장점**
        - 데이터 중복 제거 - 게시글마다 작성자 정보를 복사할 필요 없다
        - 수정 용이 - 회원 이름 변경 시 회원 테이블 한 곳만 수정
- ERD란?

  ### 1. ERD (Entity-Relationship Diagram)

    - 데이터베이스 구조를 시각적으로 표현한 설계도.
    - 어떤 데이터를 저장하고 그것들이 서로 어떻게 연결되는지를 그림으로 나타낸다.

  ### 2. 3가지 구성 요소

    1. **Entity (개체)**
    - 저장할 대상. 테이블이 된다.
        - 회원, 게시글, 댓글, 상품, 주문
        - 명사로 표현
        - 사각형으로 그린다.
    1. **Attribute (속성)**
    - Entity가 가지는 정보. 컬럼이 된다.
        - 회원 → 이름, 이메일, 가입일
        - 게시글 → 제목, 내용, 작성일
    1. **Relationship (관계)**
    - Entity 간의 연결. 선으로 표현한다.
        - 회원 **이 작성한다** 게시글
        - 게시글 **에 달린다** 댓글
        - 동사로 표현

  ### 3. 관계의 종류 (Catdinality)

  | 관계 | 의미 | 예시 |
      | --- | --- | --- |
  | 1:1 | 하나가 하나에 대응 | 회원 — 프로필 |
  | 1:N | 하나가 여럿에 대응 | 회원 — 게시글 |
  | N:M | 여럿이 여럿에 대응 | 학생 — 수강과목 |
- 연관관계란? 그리고 연관관계를 설정하는 방법은?

  ### 1. 연관관계

    - 테이블끼리 서로 연결된 관계. 한 테이블의 데이터가 다른 테이블의 데이터를 가리키는 것.
    - **왜 필요한가?**
        - 한 테이블에 모든 정보를 넣으면 중복이 생긴다.


            | 게시글 | 작성자 | 작성자 이메일 |
            | --- | --- | --- |
            | 안녕하세요 | 김철수 | kim@a.com |
            | 질문있어요 | 김철수 | kim@a.com |
            | 오늘 날씨 | 김철수 | kim@a.com |
        - 위 예시에서 김철수가 이메일을 바꾸면 3줄을 모두 고쳐야 한다. 하나라도 빠뜨리면 데이터가 어긋난다.
        - 따라서 테이블을 나누고 연결하면 회원 테이블 한 줄만 고치면 된다.
    
    ### 2. 관계의 종류
    
    1. **1:N (일대다) — 가장 흔함**
        - 회원 1명이 게시글 여러 개를 쓴다.
        - **설정 방법: N쪽에 FK를 둔다.**
            
            ```
            게시글 테이블에 writer_id 추가
            ```
            
        - 반대로 회원 테이블에 게시글 번호를 넣으면 안 된다. 한 칸에 여러 값을 넣을 수 없기 때문이다.
    2. **1:1 (일대일)**
        - 회원 1명이 프로필 1개를 가진다.
        - **설정 방법: 둘 중 한쪽에 FK를 둔다.**
        - 주로 **자주 조회하는 쪽** 또는 **없을 수도 있는 쪽**에 넣는다. 프로필은 없을 수 있으니 프로필 테이블에 `member_id`를 두는 편이 낫다.
            
            ```
            프로필 테이블
            id (PK) | 소개글 | member_id (FK)
            ```
            
    3. **N:M (다대다)**
        - 학생 여러 명이 과목 여러 개를 수강한다.
        - **설정 방법: 중간 테이블을 만든다.**
        - N:M은 FK 하나로 표현할 수 없다. 양쪽 어디에 FK를 넣어도 값이 여러 개가 되기 때문이다.
        
        ```
        학생 테이블            수강신청 테이블(중간)         과목 테이블
        id (PK) | 이름         id (PK)                    id (PK) | 과목명
        1       | 김철수   →   student_id (FK)      ←     1       | 자료구조
        2       | 이영희       course_id  (FK)            2       | 알고리즘
                               enrolled_at
        ```
        
        - 중간 테이블은 FK 2개를 가진다. N:M 하나가 1:N 두 개로 바뀌는 것이다.
- 정규화란?

  ### 1. 정규화 (Normalization)

    - 중복을 제거하고 데이터를 논리적으로 저장하기 위해 테이블을 나누는 과정.
    - 하나의 테이블에 모든 정보를 담으면 같은 값이 반복되고, 수정할 때 문제가 생긴다. 이를 단계적으로 해소하는 설계 기법이다.

  ### 2. 왜 필요한가: 이상 현상

    - 정규화되지 않은 테이블에서 발생하는 문제.


        | 학번 | 이름 | 학과 | 학과사무실 | 과목 |
        | --- | --- | --- | --- | --- |
        | 1 | 김철수 | 컴공 | 3층 201호 | 자료구조 |
        | 1 | 김철수 | 컴공 | 3층 201호 | 알고리즘 |
        | 2 | 이영희 | 경영 | 5층 302호 | 회계학 |
    - **삽입 이상**
        - 아직 수강신청하지 않은 학생들을 등록할 수 없다. 과목 칸을 비워야 하는데, 그러면 불완전한 데이터가 들어간다.
    - **수정 이상**
        - 컴공 사무실이 이전하면 관련된 모든 행을 고쳐야 한다. 하나라도 빠뜨리면 같은 학과인데 사무실이 다른 모순이 생긴다.
    - **삭제 이상**
        - 이영희가 회계학 수강을 취소하면 그 행이 사라지면서 “경영학과 사무실은 5층 302호”라는 정보까지 함께 사라진다.
    
    ### 3. 1NF (제1정규형)
    
    - **규칙: 모든 칸에 값이 하나만 들어간다.**
    - 한 칸에 여러 값을 넣거나, 같은 의미의 컬럼을 여러 개 만들면 안된다.
    - **위반**
        
        
        | 학번 | 이름 | 과목 |
        | --- | --- | --- |
        | 1 | 김철수 | 자료구조, 알고리즘 |
    - **해결** — 행으로 분리
        
        
        | 학번 | 이름 | 과목 |
        | --- | --- | --- |
        | 1 | 김철수 | 자료구조 |
        | 1 | 김철수 | 알고리즘 |
    - 한 칸에 `자료구조, 알고리즘`이 들어 있으면 "알고리즘 수강생 수"를 세는 쿼리를 쓸 수 없다. 문자열을 잘라 처리해야 하는데 이는 인덱스도 못 타고 느리다.
    
    ### 4. 2NF (제2정규형)
    
    - **규칙: 1NF를 만족하고, PK 전체에 의존하지 않는 컬럼을 분리한다.**
    - PK가 여러 컬럼으로 이루어졌을 때(복합키), 그중 일부에만 딸려 있는 컬럼이 문제다. 이를 **부분 함수 종속**이라 한다.
    - **위반** — PK는 (학번 + 과목코드)
        
        
        | 학번 | 과목코드 | 성적 | 학생이름 |
        | --- | --- | --- | --- |
        | 1 | CS101 | A | 김철수 |
        | 1 | CS102 | B | 김철수 |
        - `성적`은 학번과 과목코드 둘 다 있어야 정해진다. 하지만 `학생이름`은 **학번만으로** 정해진다. 그래서 김철수가 계속 반복된다.
    - **해결** — 분리
        
        **수강 테이블**
        
        | 학번 | 과목코드 | 성적 |
        | --- | --- | --- |
        | 1 | CS101 | A |
        | 1 | CS102 | B |
        
        **학생 테이블**
        
        | 학번 | 학생이름 |
        | --- | --- |
        | 1 | 김철수 |
    
    ### 5. 3NF (제3정규형)
    
    - **규칙: 2NF를 만족하고, 일반 컬럼에 딸려 있는 컬럼을 분리한다.**
    - PK가 아닌 컬럼이 다른 일반 컬럼에 의존하는 것을 **이행적 종속**이라 한다.
    - **위반** — PK는 학번
        
        
        | 학번 | 이름 | 학과 | 학과사무실 |
        | --- | --- | --- | --- |
        | 1 | 김철수 | 컴공 | 3층 201호 |
        | 2 | 박민수 | 컴공 | 3층 201호 |
        - `학과사무실`은 학번이 아니라 **학과**에 딸려 있다. 학번 → 학과 → 학과사무실로 한 단계 건너뛰어 연결된다.
    - **해결** — 분리
        
        **학생 테이블**
        
        | 학번 | 이름 | 학과코드 (FK) |
        | --- | --- | --- |
        | 1 | 김철수 | C01 |
        | 2 | 박민수 | C01 |
        
        **학과 테이블**
        
        | 학과코드 | 학과명 | 학과사무실 |
        | --- | --- | --- |
        | C01 | 컴공 | 3층 201호 |
    - 이제 사무실이 이전해도 학과 테이블 한 줄만 고치면 된다.
- 반 정규화란?

  ### 1. 반정규화 (Denormalization)

    - 성능을 위해 정규화를 일부러 되돌려 중복을 허용하는 것.

  ### 2. 왜 필요한가

    - 정규화하면 테이블이 잘게 나뉜다 → JOIN이 많아진다 → 조회가 느려진다.
    - 읽기가 쓰기보다 훨씬 많다면, 중복을 조금 허용하는 편이 이득일 수 있다.

  ### 3. 방법

    1. 중복 컬럼 추가
        - 게시글 테이블에 `writer_name`을 복사해둔다 → JOIN 없이 작성자 이름 조회.
    2. **집계 컬럼 추가** (가장 흔함)
        - 게시글 테이블에 `comment_count`를 저장 → 매번 `COUNT` 안 해도 된다.
    3. **테이블 병합**
        - 항상 같이 조회하는 1:1 테이블을 하나로 합친다.
    4. **테이블 분할**
        - 목록에 안 쓰는 무거운 컬럼(본문 등)을 따로 뺀다.

  ### 4. 언제 하는가

    ```
    정규화로 설계 → 운영 → 느린 곳 측정 → 인덱스로 해결 시도 → 안 되면 반정규화
    ```

    - **처음부터 하지 않는다.** 실제로 느린 게 확인된 곳만 골라서 한다. 대부분의 느린 쿼리는 인덱스로 해결된다.
    - **하면 안 되는 곳**: 자주 바뀌는 데이터, 금액·재고처럼 정합성이 중요한 데이터.
- DB에서의 상속 관계 표현은 어떻게 하는가?

  ### 문제

    - 객체지향에는 상속이 있지만 **관계형 DB에는 상속 개념이 없다.** 테이블은 평평한 표일 뿐이다.

    ```
    상품 (이름, 가격)
     ├─ 도서 (저자, ISBN)
     ├─ 앨범 (아티스트)
     └─ 영화 (감독)
    ```

    - 공통 속성과 고유 속성이 섞인 이런 구조를 테이블로 옮기는 방법이 3가지 있다.

  ### 1. 단일 테이블

    - **테이블 하나에 전부 넣고, 구분 컬럼으로 타입을 나눈다.**

  | id | type | 이름 | 가격 | 저자 | 아티스트 | 감독 |
      | --- | --- | --- | --- | --- | --- | --- |
  | 1 | BOOK | 자바책 | 20000 | 김철수 | NULL | NULL |
  | 2 | ALBUM | 좋은날 | 15000 | NULL | 아이유 | NULL |
  | 3 | MOVIE | 기생충 | 12000 | NULL | NULL | 봉준호 |
    - `type` 컬럼으로 어떤 종류인지 구분한다.
    - **장점**: JOIN 없음, 조회 가장 빠름, 구조 단순
    - **단점**: NULL이 많아짐, 종류가 늘수록 컬럼이 계속 늘어남
    - **제약**: 자식 고유 컬럼에 `NOT NULL`을 걸 수 없다 (다른 타입은 그 값이 없으니까)

    ---

  ### 2. 조인 (부모 + 자식 분리)

    - **공통 속성은 부모 테이블에, 고유 속성은 자식 테이블에 나눈다.**

    ```
    상품 테이블
    id (PK) | type  | 이름   | 가격
    1       | BOOK  | 자바책 | 20000
    2       | ALBUM | 좋은날 | 15000
    
    도서 테이블
    item_id (PK, FK) | 저자
    1                | 김철수
    
    앨범 테이블
    item_id (PK, FK) | 아티스트
    2                | 아이유
    ```

    - 자식 테이블의 PK가 곧 부모를 가리키는 FK다.
    - 조회할 때 JOIN으로 합친다.

    ```sql
    SELECT i.이름, i.가격, b.저자FROM 상품 iJOIN 도서 b ON i.id = b.item_id;
    ```

    - **장점**: 정규화된 구조, NULL 없음, 공간 효율적, `NOT NULL` 제약 가능
    - **단점**: 조회 시 JOIN 필요, 저장할 때 테이블 2곳에 INSERT
    - **가장 정석적인 방식**

    ---

  ### 3. 테이블별 분리

  **부모 테이블 없이, 자식 테이블마다 공통 컬럼을 복사한다.**

    ```
    도서 테이블
    id (PK) | 이름   | 가격  | 저자
    
    앨범 테이블
    id (PK) | 이름   | 가격  | 아티스트
    ```

    - **장점**: 특정 타입만 다룰 때 단순
    - **단점**: "전체 상품 조회"를 하려면 모든 테이블을 `UNION` 해야 함, 공통 컬럼이 중복되어 수정 시 여러 곳을 고쳐야 함
    - **권장하지 않음**

  ### 4. 선택기준

  | 상황 | 전략 |
      | --- | --- |
  | 자식별 고유 컬럼이 적고 종류도 적음 | 단일 테이블 |
  | 자식마다 컬럼이 많고 서로 다름 | 조인 |
  | 데이터가 많고 정합성이 중요 | 조인 |
  | 타입 전체를 한 번에 조회할 일이 잦음 | 단일 테이블 or 조인 |
    - **기본은 조인.** 구조가 단순하고 조회 성능이 중요하면 단일 테이블. 테이블별 분리는 거의 쓰지 않는다.
- 인덱스란?

  ### 1. 인덱스 (Index)

    - 조회 속도를 높이기 위해 컬럼 값을 미리 정렬해둔 별도의 자료구조.
    - 책 뒤의 **색인**과 같다. 처음부터 다 넘겨보는 대신, 색인에서 찾아 해당 페이지로 바로 간다.

  ### 2. 장점

    - 조회(SELECT) 속도 향상
    - 범위 검색, 정렬(`ORDER BY`) 빠름
    - JOIN 성능 향상

  ### 3. 단점

    - INSERT / UPDATE / DELETE 느려짐 (인덱스도 같이 갱신)
    - 저장 공간 추가 소모
    - 많이 만들수록 관리 부담 증가

  ### 4. 종류

  | 종류 | 설명 |
      | --- | --- |
  | 단일 인덱스 | 컬럼 1개 |
  | 복합 인덱스 | 컬럼 여러 개 묶음 (순서 중요) |
  | 유니크 인덱스 | 중복 값 불허 |
  | 클러스터형 | 데이터 자체가 정렬됨 (PK, 테이블당 1개) |
  | 논클러스터형 | 위치 정보만 저장 (여러 개 가능) |
    - **인덱스 걸어야 할 컬럼**
        - `WHERE`에 자주 쓰이는 컬럼
        - FK (JOIN 컬럼)
        - `ORDER BY` 컬럼
        - 값 종류가 많은 컬럼
    - **인덱스 걸면 안 되는 컬럼**
        - 값 종류가 적은 컬럼 (성별, Y/N)
        - 자주 변경되는 컬럼
        - 데이터가 적은 테이블
