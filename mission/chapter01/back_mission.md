### 관계 구조

```
member (1) ──< member_term (N) >── (1) term
member (1) ──< member_prefer_food (N) >── (1) food_category
member (1) ──< member_mission (N) >── (1) mission

region (1) ──< store (N)
food_category (1) ──< store (N)
store (1) ──< mission (N)
```

N:M 관계 3개를 중간 테이블로 분해했다.

| 개념상 관계 | 중간 테이블 |
| --- | --- |
| 회원 ↔ 약관 | `member_term` |
| 회원 ↔ 음식 종류 | `member_prefer_food` |
| 회원 ↔ 미션 | `member_mission` |

### 주요 설계 결정

#### 1. 소셜 로그인 식별

`social_type`(카카오/네이버/애플/구글)과 `social_id`를 분리 저장하고, 두 컬럼 조합에 UNIQUE를 걸었다.

소셜 제공자마다 ID 체계가 달라 `social_id`만으로는 충돌 가능성이 있고, 조합으로 관리해야 같은 계정의 중복 가입도 차단된다.

#### 2. 약관 동의를 테이블로 분리

초기에는 `term1_yn` ~ `term5_yn` 형태로 설계했으나 변경했다.

**변경 이유**

- 약관이 추가되면 테이블 구조를 변경해야 함 (1NF 위반)
- 컬럼명만으로 어떤 약관인지 알 수 없음
- 약관 개정 시 어느 버전에 동의했는지 추적 불가
- 약관별 동의 시각 기록 불가 — 마케팅 수신 동의는 법적으로 시각 기록이 필요

약관 마스터와 동의 내역을 분리해, 약관이 추가되면 행만 넣으면 되도록 했다.

#### 3. 지역과 주소의 역할 분리

|  | 용도 |
| --- | --- |
| 주소 | 실제 위치 (자유 입력 문자열) |
| 지역 | 서비스 운영 구역 (고정 선택지) |

주소 문자열은 표기가 제각각이라 그룹핑이 불가능하다. 지역별 가게 조회를 위해 지역을 별도 테이블로 두고 가게에서 FK로 참조했다.

#### 4. 음식 분류 테이블 재사용

회원의 선호 음식과 가게 분류에 동일한 테이블을 사용한다. 같은 분류 체계를 쓰므로 나눌 이유가 없다.

- 회원 → 선호 음식 (복수 선택, 중간 테이블)
- 가게 → 음식 종류 (단일, FK)

#### 5. 미션 조건 처리

화면 표시용 문구(문자열)와 판정용 금액(정수)을 함께 저장한다.

금액 컬럼은 NULL 허용. "리뷰 작성"처럼 금액 조건이 없는 미션이 존재할 수 있기 때문이다. **조건 없음은 NULL, 0원 조건은 0**으로 구분된다.

현재 범위에서는 주문 데이터가 없어 자동 판정을 하지 않고, 사용자의 '성공 요청'으로 상태를 변경한다.

#### 6. Soft Delete

전 테이블에 `deleted_at`을 두어 물리 삭제 대신 논리 삭제를 사용한다. 값이 NULL이면 활성 데이터다.

#### 7. 공통 규칙

- PK는 `id BIGINT AUTO_INCREMENT` 단독 사용
- 중간 테이블도 복합키 대신 단일 PK + UNIQUE 제약
- 날짜/시간은 `DATETIME` 단일 컬럼 (문자열 분리 저장 지양)
- 고정 선택지는 `ENUM` 사용 (성별, 탈퇴 여부, 소셜 타입)
